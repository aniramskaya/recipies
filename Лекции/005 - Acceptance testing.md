#  Приемочное тестирование

Приемочное тестирование - по сути реализует набор тестов, каким пользуется хорошо подготовленный тестировщик при ручном приемочном тестировании. Это особый подкласс интеграционных тестов, которые тестируют всю фичу/экран целиком - от входа пользователя до получения конечного результата.

Приемочные тесты взаиможействуют с фичой **от лица пользователя**. По этой причине в приемочных тестах немного меняется терминология. Слово sut можно заменить на feature, различные нажатия на кнопки и другие действия содержат слово user, а имитация ответов с бэка сполне может содержать слово server. Такая "подмена" лексики немного очеловечивает код самих тестов. В идеале они должны читаться почти как обычный текст.

Простой пример
 ```swift
@Test func loadingErrorScenario() async throws {
    let (feature, server) = makeFeature()
    let error = DomainError.uknown()
    
    feature.start()
        
    feature.assertIsDisplayingLoadingState()

    server.respondWithError(error)
    
    feature.assertIsDisplayingError(text: "Не удалось загрузить список рецептов")
}
 ```


Благодаря использования такой лексики, приемочные тесты выступают не только в качестве средства тестирования, но и в качестве документации и средства коммуникации с теми, кто придет вносить изменения в фичу в будущем. Код, терминология в котором максимально приближена к человеческому языку, имеет очень высокую степень читабельности и дает понимание того, **как именно работает фича**, даже если техдокументация давно утеряна или неактуальна. В этом смысле приемочные тесты - документация, актуальность которой не устаревает никогда.

Чтобы приемочные тесты не создавали ощущения нагромождения, можно прибегать к паре полезных практик:
1. В приемочных тестах мы проверяем прохождение юзера через зеленый сценарий и ключевые (но не все!) красные. Выбор ключевых сценариев может быть неочевиден с первого раза и приходит с опытом. В этом выборе всегда может помочь тестировщик, который поможет сфокусироваться на важном и повысить качество тестов.
2. Приемочные (и другие интеграционные тесты) можно комбинировать в целую историю. Например, пользователь заходит на экран -> запускается загрузка -> загрузка завершается ошибкой -> пользователь нажимает кнопку "попробовать снова" -> снова запускается загрузка -> данные успешно загружаются. Соединение нескольких шагов в историю может сделать тесты полее выразительными, но при этом лаконичными.

Пример:

 ```swift
@Test func loadingErrorScenario() async throws {
    let (feature, server, user) = makeFeature()
    let error = DomainError.uknown()
    
    feature.start()
    
    feature.assertIsDisplayingLoadingState()
        
    server.respondWithError(error)
    
    feature.assertIsDisplayingError(text: "Не удалось загрузить список рецептов")
    
    user.tapReloadButton()
    
    feature.assertIsDisplayingLoadingState()
    
    server.respondWithData(testDTO)
    
    feature.assertIsDisplayingViewModel(testViewModel)
}
 ```
 
 Приемочные тесты находятся в самой верхней части пирамиды тестирования. За счет того, что они проверяют взаимодействие пользователя и системы в рамках сценариев, даже при рефакторинге всего кода фичи они должны оставаться зелеными и не ломаться. Приемочные тесты ни в коем случае не отменяют ручной приемки человеком, но после того как эта приемка выполнена, они становятся как бы вердиктом тестировщика: "тут все проверено и работает именно так как ожидается". С этого момента они и становятся самой актуальной документацией фичи.
