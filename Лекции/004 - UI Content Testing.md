#  Тестирование контента и DSL методы

Визуальные компоненты можно тестировать не только снапшотами, но и проверять их контент. Помним, что снапшоты хороши для того, чтобы защитить себя от случайных изменений кода в будущем, но они не часть TDD методологии.

В TDD мы пишем сначала тест, а только потом код. Важнейшая суть методологии включает в себя три этапа:
**Red -> Green -> Refactor**

- Red означат что мы должны сначала написать тест, который не выполняется (или даже не компилируется, так как сущности которую тест проверяет может еще не быть)
- Green говорит о том, что мы должна сделать тест зеленым, приложив минимальные усилия
- Refactor призывает нас выполнить рефакторинг кода после того как тест стал зеленым

Важные моменты: 
- Предположим, сущность, для которой вы пишете очередной тест, уже существует, и ваш тест сразу оказался зеленым. Это всегда должно быть для вас некоторой красной лампочкой, зажигающей вопрос: "А этот тест вообще хоть что-то проверяет?" Для того чтобы ответить на этот вопрос, измените код тестируемой сущности так, чтобы ваш тест скомпилировался, но покраснел, и посмотрите внимательно на остальные тесты. Возможно, вновь написанный тест уже дублирует существующий. Фазу **Red** нельзя пропускать ни в коем случае!
- Последний шаг, **Refactor** вроде бы вполне логичная часть метода, позволяющая вам сделать код, покрытый тестами, лучше. Но это еще и огромный подарок методологии для всего проекта, а не для какого-то отдельно взятого кусочка кода. TDD дает вам свободу рефакторинга без страха что-то поломать, и, в идеале, без необходимости ручного перетестирования. Безусловно, определить необходимость ручного тестирования после рефакторинга, можно только понимая насколько хорошо ваши тесты покрывают все сценарии. Если тесты покрывают все сценарии фичи, то, пока они остаются зелеными, любой рефакторинг безопасен.
- Есть такой показатель - количество строчек кода и ветвлений, которые покрывают ваши тесты. Это чисто технический показатель, который нельзя использовать для утверждения, что код реально хорошо покрыт тестами, Единственное что может вам правдиво сообщить этот показатель: "Вы забыли написать один или несколько тестов". Реальное покрытие тестами нужно считать по сценариям. Например, в вашей фиче есть один "зеленый" путь (happy path) и несколько красных. Если вы не написали тесты хотя бы для одного из путей - ваши тесты не обладают полнотой, даже если техническое покрытие по строкам показывает 100%

## Тестирование контента

Тестирование контента дает нам возможность убедиться в том, что внутренняя логика компонента выводит на экран ожидаемые тексты, элементы и прочий контент. Тестирование контента не гарантирует что ваша верстка выполнена правильно, но оно гарантирует, что **поведение** компонента совпадает с ожидаемым.

Есть два немного отличающихся подхода к тестированию контента. 

Первый из них исходит из того, что компонент должен обеспечивать выдачу на экран контента, который видит юзер, при этом полностью игнорируя саму структуру компонента. Важно лишь то, что нужные надписи выведены на экран. При этом подходе мы воспринимаем UI компонент как черный ящик и только проверяем что переданные в модели надписи выведены на экран. Такие тесты масимально устойчивы к изменениям внутренней структуры компонента, но не защищают от ошибок, при которых мы, например, перепутали тексты заголовка и подзаголовка между собой.

Второй исходит из того, что надписи не просто должны быть выведены на экран, а выведены в правильных частях компонента. Этот подход исходит из того, что тестам известна хотя бы какая-то информация о внутренней структуре компонента. Очевидно, чем больше ваши тесты знают о внутренней структуре компонента, тем более хрупкими они становятся. Для того чтобы не сваливаться в написание хрупких тестов, нам нужен какой-то инструмент, позволяющий сделать тесты более точными, но при этом достаточно стабильными. Этот инструмент - **accessibilityIdentifier**. accessibilityIdentifier - это просто семантическая метка, некое название, присвоенное UI элементу внутри составного компонента, для использования в тестах. Вы можете сколько угодно менять внутреннюю структуру компонента, но пока идентификаторы его частей остаются неизменными, это не влияет на тесты.

По мнению автора, второй подход, хоть и добавляет чуточку хрупкости и допускает протечку деталей реализации в тесты, является хорошим компромиссом между точность и стабильностью.

## DSL хэлперы

DSL расшифровывается как Domain Specific Language. Вообще говоря, это достаточно широкое и расплывчатое понятие, но применительно к тестам это попросту такие кусочки кода, которые знают некоторые (не все!) детали реализации тестируемой сущности и используются в тестах для повышения их эффективности.

Мы можем дать нашим тестам некоторые знания о деталях реализации компонента, и написать прямо так в тексте теста:

```swift
    @Test("RecipeListRow правильно отображает контент")
    func RecipeListRowContent() throws {
        let sut = RecipeListRow(
            model: .init(
                id: UUID(uuidString: "b0a1a334-09b3-4e61-87bf-0b05745388cf")!,
                name: "Котлета по-киевски",
                imageSource: .uiImage(.make(withColor: .red)),
                cookingTimeMins: 35,
                rating: 4.6
            )
        )
        
        let inspectable = try sut.inspect()
        
        let name = try inspectable.find(viewWithAccessibilityIdentifier: A11y.name).text().string()
        #expect(name == "Котлета по-киевски")
    }
```

Но все же лучше не допускать протечек деталей реализации в сами тесты и вынести этот код в отдельный метод:

```swift
extension RecipeListRow {
    func assertIsDisplaying(title: String) throws {
        let inspectable = try self.inspect()
        
        let name = try inspectable.find(viewWithAccessibilityIdentifier: A11y.name).text().string()
        #expect(name == title)
    }
}

// А в тесте:

    @Test("RecipeListRow правильно отображает контент")
    func RecipeListRowContent() throws {
        let sut = RecipeListRow(
            model: .init(
                id: UUID(uuidString: "b0a1a334-09b3-4e61-87bf-0b05745388cf")!,
                name: "Котлета по-киевски",
                imageSource: .uiImage(.make(withColor: .red)),
                cookingTimeMins: 35,
                rating: 4.6
            )
        )
        
        sut.assertIsDisplaying(title: "Котлета по-киевски")
    }
```

Такой подход дает сразу две возможности:

1. Все знания о деталях реализации компонента находятся в DSL методе и не протекают в тесты. Код тестов остается максимально чистым и читабельным.
2. DSL методы можно повторно использовать в тестах высшего порядка, в которых, например, проверяется поведение целого экрана на котором использован UI компонент.
